# Fabric/dbt deployment skeleton (requires a real Fabric workspace)

The models here are **real dbt SQL project files**, but they have **not been exercised against a live Fabric capacity in the bundled local tests**. dbt syntax/T-SQL compatibility and compute behavior must be validated in your tenant.

## Prerequisites

- Microsoft Fabric capacity and a workspace supporting Lakehouse and Warehouse items.
- A schema-enabled Lakehouse named `bronze_lh` with SQL analytics endpoint enabled.
- A Warehouse for the candidate release, with access to the Lakehouse in the same workspace.
- dbt-fabric and ODBC Driver 18, plus Azure CLI login or a service-principal credential.

## Procedure

1. `python -m medallion_x.cli demo --scenario clean --out-dir runs/clean`
2. Upload `runs/clean/bronze_payment_events.csv` to the Bronze Lakehouse `Files/incoming` area.
3. In a Fabric notebook attached to `bronze_lh`, run `../bronze/load_raw_events.py` after configuring `INPUT_CSV`. This writes Delta table `dbo.raw_payment_events`.
4. Check the SQL analytics endpoint exposes `bronze_lh.dbo.raw_payment_events` to the **candidate Warehouse**. SQL endpoint data may take time to synchronize; don't proceed until the table is queryable.
5. `pip install dbt-fabric` and install ODBC Driver 18. Run `az login`.
6. Copy `profiles.yml.example` to `~/.dbt/profiles.yml`, export `FABRIC_SQL_SERVER`, `FABRIC_WAREHOUSE_NAME`, `FABRIC_BRONZE_LAKEHOUSE` as appropriate.
7. In this directory: `dbt debug`, then `dbt build --target dev`, then `dbt docs generate`.
8. Inspect `target/manifest.json`, then from the repository root run `medallion-x impact --manifest fabric/dbt/target/manifest.json`.
9. Create a **separate production Warehouse and dbt target**. For a code-change comparison, run baseline/candidate against a pinned or frozen Bronze snapshot, then query candidate/production Gold tables and apply the release policy before any production publication.
10. Create a **new** Direct Lake semantic model on the approved **physical** Gold tables. Validate permissions, refresh behavior and security separately.

## Important separation of responsibilities

The Python `replay` module is a local **reference model and evidence generator**, not a compiler or remote executor for the dbt SQL files. Running the local demo does not prove dbt/Fabric parity. For production promotion you must implement a read-only Fabric metric extraction step, stable input snapshot binding, and a release action that is guarded by a human approval and platform-specific rollback plan.

The built-in dbt model schemas (e.g., `analytics_dev_staging`, `analytics_dev_silver`) are generated by dbt's standard custom schema naming behavior. Do not assume they are literally named `staging`/`silver`/`gold` without configuring schema generation.

**Direct Lake caveat:** A SQL view is not a drop-in replacement for a physical Gold table under all Direct Lake configurations; SQL views may force DirectQuery fallback. Keep serving tables physical and perform a reviewed release rather than swapping a view without performance testing.

Supported product guidance: https://learn.microsoft.com/en-us/fabric/data-factory/common-dbt-job-patterns and https://docs.getdbt.com/docs/local/connect-data-platform/fabric-setup

## v2: Frozen source and isolated baseline/candidate builds

Generate an isolated experiment plan from the repository root:

```bash
python fabric/experiments/plan.py --run-id lab01 --out-dir runs/fabric-plan-lab01
```

Use `01_create_schema.sql` followed by `02_freeze_snapshot.sql` in a **freeze Warehouse**. Fabric Warehouse supports CTAS from a Lakehouse in the same workspace, so the frozen source becomes a physical Warehouse table that both dbt runs can read. Use different Warehouse items for baseline and candidate, not two mutable views on the raw Lakehouse.

The dbt source YAML supports runtime `--vars` selecting the frozen table; inspect `execution_plan.json` for exact commands. Run baseline and candidate from **separate Git worktrees/commits**, not a single checkout with a changing branch. `03_compare_outputs.sql` compares physical Gold results and a FULL OUTER JOIN of transaction state. Run tests and inspect dbt `run_results.json` and manifest in **each** worktree, capturing SHAs and query/job identifiers.

**External execution boundary:** This repo generates the deployment *plan* only. It does not automatically authenticate to Fabric, execute remote SQL, synchronize a semantic model, or publish to production. Record the frozen row count and protect the freeze schema from mutation. This is a materialized snapshot, not a guarantee about an upstream cross-table transaction boundary. Verify dbt-generated schema names in your tenant before running comparisons.
